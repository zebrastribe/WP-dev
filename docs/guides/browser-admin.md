# Browser admin (optional UI)

The optional browser UI lives at **`http://localhost:<WP_PORT>/admin/`** — same host and port as WordPress.

CLI remains fully usable without this UI (`wp-dev pull|push|backup|doctor|…`).

**Localhost only.** Do not expose `/admin/`, Docker runners, or the terminal on the public internet.

## Open admin

After `wp-dev up`:

```
http://localhost:8888/admin/
```

(Port comes from `WP_PORT` in `docker/.env`.) The header shows the project folder under **WP-dev Local**. **Unlock admin** is in the top right when the session is closed; **Sign out** is there when it is open. The token is `WPDEV_ADMIN_SAVE_TOKEN` in `docker/.env`.

## Primary navigation

| Nav | Purpose |
|-----|---------|
| **Setup** | This computer, Production, and Staging. Save the servers here. |
| **Sync** | Full site pull onto this computer, or push this computer to Staging. Preview, then Start. |
| **Backup** | Save or restore Local, Staging, or Production. |
| **Update** | WordPress, plugins, and themes on this computer. |
| **Advanced** | Extra controls. Everyday pull, push, backup, and updates stay on the four tabs above. |

### Advanced

| Group | Items |
|-------|--------|
| **Copying** | **Full site rules** (what a full site sync copies). **Theme files** (CSS/JS only; the database stays). |
| **This computer** | Project files, PHP, services, terminal, update wp-dev. |
| **Recovery** | Restore points, config file, docs. |

### Sync (what to use when)

| Lane | Use for | CLI |
|------|---------|-----|
| **Staging → Local** / **Production → Local** | Copy a server onto this computer (files and database) | `pull staging` / `pull production` |
| **Local → Staging** | Copy this computer to Staging after Preview | `push staging` |
| **Theme files** (Advanced) | Theme CSS/JS only. Does not replace the database. | `push theme` / `pull theme` |
| Full-site **Local → Production** | Not offered | — |
| A host ending in `.invalid` | Not a server. Save a real host on Setup. Pull and push stop before SSH. | — |

Full site rules do not apply to Theme files.

### Backup / restore

- Staging/Production backups in the UI default to **database only** (those `.sql` files restore in the browser).
- Backup types: **Database**, **Content** (`backup --files`), and **Complete** (`backup --complete`) for Dev, Staging, and Production. Complete is best before updates; restore keeps live `wp-config.php`.
- **Advanced → Restore points** is the longer list / timeline for the same backup store.

## Security (localhost)

**The admin must never be exposed beyond localhost (Gate 0).** It provides access to staging DB secrets, the terminal, backup/restore runners, and config/.env writes.

### Gate 0: Network-level protection

The admin API enforces two-layer localhost verification:

1. **Host header check** — Must be `localhost`, `127.0.0.1`, or `[::1]`. Blocks DNS rebinding attacks where an attacker's domain resolves to 127.0.0.1.

2. **REMOTE_ADDR check** — The client's actual network address must be:
   - Loopback (`127.0.0.1`, `::1`), or
   - The trusted Docker network gateway (from `WPDEV_ADMIN_TRUSTED_GATEWAY`)

   This blocks attackers who spoof `Host: localhost` headers from a different network position. The trusted gateway is detected from the actual Docker network during `wp-dev up`.

3. **X-Forwarded-For restriction** — The `remoteip.conf` file (generated by `wp-dev up`) restricts which IPs can set the `X-Forwarded-For` header. Only the SSL proxy's fixed IP is trusted, preventing containers or LAN hosts from spoofing `REMOTE_ADDR`.

4. **Defense-in-depth for auto-unlock** — Additionally requires `WPDEV_WP_BIND_LOCAL=1`, confirming the WordPress port is published on `127.0.0.1` only. Catches edge cases where Docker relays LAN traffic through the gateway (rootless Docker, Docker Desktop, hairpin NAT).

### Security environment variables

Set in `docker/.env` by `wp-dev up`:

| Variable | Purpose |
|----------|---------|
| `WPDEV_ADMIN_SAVE_TOKEN` | Unlock admin / save config (session cookie after unlock) |
| `WPDEV_TERMINAL_AUTH` | Interactive terminal login (`user:password`) |
| `WPDEV_TERMINAL_RUNNER_TOKEN` | Server-side runners only (PHP proxy; **not** sent to browser) |
| `WP_BIND` | Bind address for published ports (`127.0.0.1` = localhost only) |
| `WPDEV_NETWORK_SUBNET` | Docker network subnet for this stack (auto-allocated) |
| `WPDEV_NETWORK_GATEWAY` | Docker network gateway (detected from network) |
| `WPDEV_ADMIN_TRUSTED_GATEWAY` | Trusted gateway for REMOTE_ADDR checks (synced from gateway) |
| `WPDEV_WP_BIND_LOCAL` | `1` if `WP_BIND` is localhost (derived, not overwritten if explicit) |
| `WPDEV_SSL_PROXY_IP` | Fixed IP for SSL proxy (for remoteip.conf trust) |

### Other localhost hardening

- Auto-unlock requires a same-origin browser request (not in-container curl alone).
- Auto-unlock requires a prior challenge cookie from GET auth-status (blocks one-shot header spoofs).
- Interactive terminal runs without Docker CLI access; sync runners keep `docker.sock` for pull/push.
- Terminal uses origin checking (`-O` flag) for CSRF protection.
- `docker/.env` is kept owner+www-data readable (`660`), not world-readable.
- Two stacks on one host get unique subnets automatically (no conflicts).

### Migration from older versions

If upgrading from a version before Gate 0 network checks:

1. Run `wp-dev down` to stop the current stack
2. Run `wp-dev up` — this will:
   - Allocate a unique subnet for your stack
   - Detect the network gateway
   - Generate `docker/remoteip.conf`
   - Set all security environment variables
3. Containers are recreated on the new network
4. The old `<project>_default` network is left behind (safe to remove with `docker network rm`)
5. The `db_data` volume is preserved — your database is not affected

**Never run `docker compose down -v`** — this removes volumes including your database.

### LAN exposure (not supported)

Exposing the admin beyond localhost is not supported and not recommended. The security model assumes localhost-only access. If you set `WP_BIND=0.0.0.0`:

- `WPDEV_WP_BIND_LOCAL` will be `0` (derived from `WP_BIND`)
- Auto-unlock will be disabled
- You must manually unlock with the token
- **There is no additional authentication** — anyone who can reach the port can attempt brute-force attacks on the token

If you need remote access, use SSH port forwarding instead: `ssh -L 8888:localhost:8888 yourhost`.

npm run admin:build:wp
```

npm run admin:dev
```

## Local acceptance checklist

When dogfooding the browser UI:

- The header shows the project folder. A closed session shows **Unlock admin**; an open session shows **Sign out**.
- Sync offers Staging → Local, Production → Local, and Local → Staging. Full-site Local → Production is not a button. Preview runs before Start.
- A Staging host ending in `.invalid` shows “not set up yet” and does not ask you to pin `known_hosts`.
- Theme files live under Advanced → Copying. They do not replace the database.
- Backup still restores on the Backup page. Advanced → Restore points is the longer list.
- Advanced → Terminal is a shell on this computer, not a full-site production push.
- Every UI action still maps to an existing CLI command (`push` / `pull` / `backup` / `doctor` / …)

## Shared package

Primary pages + adapter types live in [`packages/wpdev-web`](../../packages/wpdev-web/README.md) (`@wpdev/web`). `docs/admin` is a thin Vite shell: auth, theme, and `@wpdev/web-host` → local runners. WP-dev Cloud keeps its own job panels and uses the same tab names. It does not mount this wizard.
